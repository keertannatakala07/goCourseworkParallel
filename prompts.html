In Go, channels are usually the cleanest solution, but there are several strategies depending on what you mean by "pause the main loop".

1. Block on a channel (idiomatic Go)

Keyboard goroutine signals the main loop:

Go
pause := make(chan struct{})
 
go func() {
for {
key := readKey()
if key == 'p' {
pause <- struct{}{}
}
}
}()
 
for {
<-pause // waits until signal arrives
 
fmt.Println("Paused")
}

Or toggle pause/resume:

Go
paused := false
 
for {
select {
case <-pauseCh:
paused = !paused
default:
}
 
if paused {
time.Sleep(50 * time.Millisecond)
continue
}
 
// normal work
}

2. Shared atomic variable

If the keyboard goroutine just needs to set a flag:

Go
var paused atomic.Bool
 
go func() {
for {
if readKey() == 'p' {
paused.Store(true)
}
}
}()
 
for {
if paused.Load() {
continue
}
 
// work
}

Good for simple state sharing.

3. Mutex + condition variable (sync.Cond)

Useful when you want the main loop to sleep until resumed rather than busy-waiting.

Go
var mu sync.Mutex
cond := sync.NewCond(&mu)
 
paused := false
 
go func() {
for {
key := readKey()
 
mu.Lock()
if key == 'p' {
paused = true
}
if key == 'r' {
paused = false
cond.Signal()
}
mu.Unlock()
}
}()
 
for {
mu.Lock()
for paused {
cond.Wait()
}
mu.Unlock()
 
// do work
}

This is essentially the Go equivalent of a pause/resume mechanism.

4. Context cancellation

If pausing actually means stopping and restarting work:

Go
ctx, cancel := context.WithCancel(context.Background())
 
go worker(ctx)
 
if key == 'q' {
cancel()
}

More for shutdown than pause.

5. Semaphore pattern

A buffered channel with capacity 1 can act like a pause lock:

Go
gate := make(chan struct{}, 1)
gate <- struct{}{} // unlocked
 
// main loop
for {
<-gate
gate <- struct{}{}
 
// work
}

The keyboard goroutine can hold the token to block execution.

What's most common?

For a game loop, TUI, or interactive terminal program:

  • Pause/resume state → atomic bool or mutex-protected bool.
  • Wait until resumed → sync.Cond.
  • One-off notifications → channels.
  • Stop program → context.Context.

If your keyboard handler is running in a goroutine and you want the main loop to truly freeze until another key is pressed, sync.Cond is often the best fit. If you just need a paused flag checked each iteration, an atomic.Bool is simplest.

The usual approaches are:

1. Block on a channel (most Go-like)

Go
resume := make(chan struct{})
paused := false

go func() {
for {
key := readKey()
 
if key == 'p' {
if paused {
resume <- struct{}{}

}()

if paused {
<-resume // sleep here until resumed

}

The goroutine is literally asleep while paused.

2. sync.Cond (classic pause/resume)

Go
var (
paused bool
mu sync.Mutex
cond = sync.NewCond(&mu)
)
 
func togglePause() {
mu.Lock()
paused = !paused
 
if !paused {
cond.Signal()
}
mu.Unlock()
}
 
for {
mu.Lock()
for paused {
cond.Wait()
}
mu.Unlock()
 
// work
}

cond.Wait() puts the goroutine to sleep with essentially zero CPU usage.

3. Let the main loop receive keyboard events

Sometimes the simplest solution is to avoid sharing state:

Go
for {
select {
case key := <-keyPresses:
if key == 'p' {
paused = !paused
}
default:
if !paused {
// work
}
}
}

Which would I use?

If you're making a game, TUI, emulator, etc., where pressing P should pause and then pressing P again should resume, I'd usually use a channel or sync.Cond.

A loop like:

Go
for paused {
}

is definitely something to avoid because it'll peg a CPU core at 100%. Blocking primitives (<-ch, cond.Wait(), mutexes, etc.) are designed specifically to put the goroutine to sleep until an event occurs.

When you say "pause the main execution loop", you don't want:

Go
for paused {
// burns CPU

Instead, the main loop itself blocks until the keyboard goroutine wakes it up.

Example:

Go
var (
paused = false
resume = make(chan struct{})
)
 
go func() {
for {
key := readKey()
 
if key == 'p' {
if paused {
paused = false
resume <- struct{}{} // wake main loop
} else {
paused = true
}
}
}
}()
 
for {
if paused {
<-resume // main loop sleeps here
}
 
// main work
}

The keyboard goroutine keeps running. The main loop stops at:

Go
<-resume

which uses 0% CPU because the goroutine is blocked by the Go scheduler.

You can think of channels, sync.Cond.Wait(), mutex locks, etc. as ways to put a goroutine to sleep rather than repeatedly checking a boolean.

If all you have is a shared paused bool, there is no magic way for the main loop to know it changed without either:

  1. Polling (for paused {} or periodic checks), or
  2. Being notified via a synchronization primitive (channel, sync.Cond, semaphore, etc.).

So for a pause/unpause keybind, the typical Go solution is:

  • keyboard goroutine detects p
  • sends a signal on a channel (or signals a sync.Cond)
  • main loop blocks waiting for that signal when paused

rather than trying to watch a boolean continuously.

Copilot said:

They're related, but there's a key difference in who is doing the blocking and how they get woken up.

Blocking on a channel

Go
<-resume

The goroutine stops and waits for someone to send:

Go
resume <- struct{}{}

This is a direct one-to-one synchronization event.

Think:

"Don't continue until I receive a message."

Waiting on a condition variable

Go
cond.Wait()

This is usually paired with some shared state:

Go
for paused {
cond.Wait()
}

and then another goroutine changes the state and signals:

Go
paused = false
cond.Signal()

Think:

"Don't continue while this condition is true."

Why sync.Cond exists

You could implement a pause/resume mechanism with channels:

Go
if paused {
<-resume
}

but once you have:

  • multiple waiting goroutines
  • shared state protected by a mutex
  • need to wake one waiter (Signal)
  • need to wake all waiters (Broadcast)

sync.Cond becomes more natural.

Example:

Go
mu.Lock()
for paused {
cond.Wait()
}
mu.Unlock()

When Wait() runs it:

  1. Unlocks mu
  2. Sleeps
  3. Gets signalled
  4. Re-locks mu
  5. Returns

That's something channels don't do for you automatically.

For your pause key

If there is exactly one main loop that should pause and resume, I'd probably use a channel:

Go
pause := false
resume := make(chan struct{})
 
if pause {
<-resume
}

Simple and obvious.

If you're already protecting state with a mutex:

Go
mu.Lock()
for paused {
cond.Wait()
}
mu.Unlock()

then sync.Cond fits better.

A good rule:

  • Channel = "an event happened."
  • Cond = "wait until some shared state becomes true/false."

Your pause flag is really shared state, so sync.Cond is arguably the more textbook solution, but many Go programmers would still reach for a channel because it's simpler.

A useful mental model is:

  • Channels are for events/messages.
  • sync.Cond is for state changes.

Use a channel when...

Something happens and you want to notify another goroutine.

Go
pauseCh <- true
Go
<-pauseCh

Examples:

  • Key pressed
  • HTTP request received
  • Worker finished a job
  • Timer expired

The receiver doesn't necessarily care about shared state. It just cares that an event occurred.

Use sync.Cond when...

You have shared state and want to wait until that state satisfies some condition.

Go
for paused {
cond.Wait()
}

Example:

Go
var paused bool

The main loop isn't interested in a "resume event". What it really wants is:

"Wait while paused == true."

That's exactly what condition variables are designed for.

Go
mu.Lock()
for paused {
cond.Wait()
}
mu.Unlock()

Then:

Go
mu.Lock()
paused = false
cond.Signal()
mu.Unlock()

Why not always use channels?

Imagine multiple places can pause/unpause:

Go
paused = true
paused = false
paused = true
paused = false

With channels you're often inventing a protocol:

Go
pauseCh <- Pause
pauseCh <- Resume

and keeping state somewhere else anyway.

With sync.Cond, the state is the source of truth:

Go
paused = true

and waiters simply check that state.

Practical rule

For your specific case (press P to toggle pause):

I'd probably choose sync.Cond because "paused" is a piece of shared state.

Go
for paused {
cond.Wait()
}

reads almost like English.

For something like:

Go
key := <-keyPresses

I'd use a channel because that's an event stream.

So:

  • Keyboard input arrives → channel
  • Program should wait until paused becomes false → sync.Cond

That's the distinction most Go programmers use.

Exactly.

With a channel, you're waiting for an event:

Go
<-resumeCh

Meaning:

"Wake me up when someone sends a message."

With sync.Cond, you're waiting for a condition on shared state:

Go
for paused {
cond.Wait()
}

Meaning:

"Sleep while paused is true."

The important thing is that cond.Wait() is not constantly checking the variable. It isn't polling.

Internally it:

  1. Goes to sleep.
  2. Another goroutine changes state:
Go
paused = false
  1. That goroutine calls:
Go
cond.Signal()
  1. The sleeping goroutine wakes up and re-checks:
Go
for paused {
cond.Wait()
}

So you're still relying on a notification (Signal()), but the notification means:

"The state may have changed, check again."

rather than:

"Here's an event/message."

That's why you'll almost always see:

Go
for paused {
cond.Wait()
}

instead of:

Go
if paused {
cond.Wait()
}

because the signal doesn't guarantee the state is what you want, only that it's worth checking.

A nice way to think about it:

Channelssync.Cond
Wait for an eventWait for a state
"A key was pressed""paused == false"

ch <- valuecond.Signal()

For your pause example, the state-oriented version feels very natural:

Go

// continue game loop

because the thing you're actually interested in is not the P key press, it's whether the program is currently paused or not.

In Go, channels are usually the cleanest solution, but there are several strategies depending on what you mean by "pause the main loop".

1. Block on a channel (idiomatic Go)

Keyboard goroutine signals the main loop:

Go
pause := make(chan struct{})
 
go func() {
    for {
        key := readKey()
        if key == 'p' {
            pause <- struct{}{}
        }
    }
}()
 
for {
    <-pause // waits until signal arrives
 
    fmt.Println("Paused")
}

Or toggle pause/resume:

Go
paused := false
 
for {
    select {
    case <-pauseCh:
        paused = !paused
    default:
    }
 
    if paused {
        time.Sleep(50 * time.Millisecond)
        continue
    }
 
    // normal work
}
2. Shared atomic variable

If the keyboard goroutine just needs to set a flag:

Go
var paused atomic.Bool
 
go func() {
    for {
        if readKey() == 'p' {
            paused.Store(true)
        }
    }
}()
 
for {
    if paused.Load() {
        continue
    }
 
    // work
}

Good for simple state sharing.

3. Mutex + condition variable (sync.Cond)

Useful when you want the main loop to sleep until resumed rather than busy-waiting.

Go
var mu sync.Mutex
cond := sync.NewCond(&mu)
 
paused := false
 
go func() {
    for {
        key := readKey()
 
        mu.Lock()
        if key == 'p' {
            paused = true
        }
        if key == 'r' {
            paused = false
            cond.Signal()
        }
        mu.Unlock()
    }
}()
 
for {
    mu.Lock()
    for paused {
        cond.Wait()
    }
    mu.Unlock()
 
    // do work
}

This is essentially the Go equivalent of a pause/resume mechanism.

4. Context cancellation

If pausing actually means stopping and restarting work:

Go
ctx, cancel := context.WithCancel(context.Background())
 
go worker(ctx)
 
if key == 'q' {
    cancel()
}

More for shutdown than pause.

5. Semaphore pattern

A buffered channel with capacity 1 can act like a pause lock:

Go
gate := make(chan struct{}, 1)
gate <- struct{}{} // unlocked
 
// main loop
for {
    <-gate
    gate <- struct{}{}
 
    // work
}

The keyboard goroutine can hold the token to block execution.

What's most common?

For a game loop, TUI, or interactive terminal program:

Pause/resume state → atomic bool or mutex-protected bool.
Wait until resumed → sync.Cond.
One-off notifications → channels.
Stop program → context.Context.

If your keyboard handler is running in a goroutine and you want the main loop to truly freeze until another key is pressed, sync.Cond is often the best fit. If you just need a paused flag checked each iteration, an atomic.Bool is simplest.

    mu.Lock()

        cond.Wait()

If you're making a game, TUI, emulator, etc., where pressing P should pause and then pressing P again should resume, I'd usually use a channel or sync.Cond.

Go

}

is definitely something to avoid because it'll peg a CPU core at 100%. Blocking primitives (<-ch, cond.Wait(), mutexes, etc.) are designed specifically to put the goroutine to sleep until an event occurs.

Being notified via a synchronization primitive (channel, sync.Cond, semaphore, etc.).

keyboard goroutine detects p
sends a signal on a channel (or signals a sync.Cond)

They're related, but there's a key difference in who is doing the blocking and how they get woken up.

Blocking on a channel
Go
<-resume

The goroutine stops and waits for someone to send:

Go
resume <- struct{}{}

This is a direct one-to-one synchronization event.

Think:

"Don't continue until I receive a message."

Waiting on a condition variable
Go
cond.Wait()

This is usually paired with some shared state:

Go
for paused {
    cond.Wait()
}

and then another goroutine changes the state and signals:

Go
paused = false
cond.Signal()

Think:

"Don't continue while this condition is true."

Why sync.Cond exists

You could implement a pause/resume mechanism with channels:

Go
if paused {
    <-resume
}

but once you have:

multiple waiting goroutines
shared state protected by a mutex
need to wake one waiter (Signal)
need to wake all waiters (Broadcast)

sync.Cond becomes more natural.

Example:

Go
mu.Lock()
for paused {
    cond.Wait()
}
mu.Unlock()

When Wait() runs it:

Unlocks mu
Sleeps
Gets signalled
Re-locks mu
Returns

That's something channels don't do for you automatically.

For your pause key

If there is exactly one main loop that should pause and resume, I'd probably use a channel:

Go

    <-resume
}

Simple and obvious.

If you're already protecting state with a mutex:

Go

for paused {
    cond.Wait()
}
mu.Unlock()

then sync.Cond fits better.

A good rule:

Channel = "an event happened."
Cond = "wait until some shared state becomes true/false."

Your pause flag is really shared state, so sync.Cond is arguably the more textbook solution, but many Go programmers would still reach for a channel because it's simpler.

Exactly.

With a channel, you're waiting for an event:

Go
<-resumeCh

Meaning:

"Wake me up when someone sends a message."

With sync.Cond, you're waiting for a condition on shared state:

Go
for paused {
    cond.Wait()
}

Meaning:

"Sleep while paused is true."

The important thing is that cond.Wait() is not constantly checking the variable. It isn't polling.

Internally it:

Goes to sleep.
Another goroutine changes state:
Go
paused = false
That goroutine calls:
Go
cond.Signal()
The sleeping goroutine wakes up and re-checks:
Go
for paused {
    cond.Wait()
}

So you're still relying on a notification (Signal()), but the notification means:

"The state may have changed, check again."

rather than:

"Here's an event/message."

That's why you'll almost always see:

Go
for paused {
    cond.Wait()
}

instead of:

Go
if paused {
    cond.Wait()
}

because the signal doesn't guarantee the state is what you want, only that it's worth checking.

A nice way to think about it:

Channels	sync.Cond
Wait for an event	Wait for a state
"A key was pressed"	"paused == false"
Data/message oriented	Shared-state oriented
ch <- value	cond.Signal()

For your pause example, the state-oriented version feels very natural:

Go
mu.Lock()
for paused {
    cond.Wait()
}
mu.Unlock()
 
// continue game loop

because the thing you're actually interested in is not the P key press, it's whether the program is currently paused or not.

what does wg.wait() do
Copilot said:

wg.Wait() is from Go's sync.WaitGroup.

It blocks the current goroutine until all registered work is finished.

Example:

Go
var wg sync.WaitGroup
 
wg.Add(2)
 
go func() {
    defer wg.Done()
    fmt.Println("Worker 1")
}()
 
go func() {
    defer wg.Done()
    fmt.Println("Worker 2")
}()
 
wg.Wait()
 
fmt.Println("All workers finished")

How it works:

wg.Add(2) says "I'm waiting for 2 things."
Each goroutine eventually calls wg.Done(), which is equivalent to:
Go
wg.Add(-1)
When the internal counter reaches 0, any goroutine blocked in:
Go
wg.Wait()

is released.

A common use case is keeping main() alive:

Go
func main() {
    var wg sync.WaitGroup
 
    wg.Add(1)
 
    go func() {
        defer wg.Done()
        doStuff()
    }()
 
    wg.Wait()
}

Without Wait(), main() might exit before the goroutine finishes.

Compared to what we were discussing earlier:

channel receive (<-ch) → wait for an event/message.
cond.Wait() → wait for a state change.
wg.Wait() → wait for a group of goroutines to finish.

So WaitGroup is not really a pause/resume mechanism. It's more of a "don't continue until these N tasks are complete" mechanism.

Copilot said:

Yes.

If you do this inside your main loop:

Go
for {
    // work
 
    wg.Wait()
 
    // more work
}

then when execution reaches:

Go
wg.Wait()

the main goroutine stops there until the WaitGroup counter reaches zero.

Example:

Go
var wg sync.WaitGroup
 
for {
    wg.Add(1)
 
    go func() {
        defer wg.Done()
        time.Sleep(5 * time.Second)
    }()
 
    fmt.Println("Waiting...")
    wg.Wait()
    fmt.Println("Finished!")
 
    break
}

Output:

Plain Text
Waiting...
(5 second pause)
Finished!

The main goroutine is blocked during those 5 seconds.

One important detail:

Go
wg.Wait()

waits for everything currently counted in that WaitGroup, not just "things started this loop iteration".

For example:

Go
wg.Add(2)
 
go worker1(&wg)
go worker2(&wg)
 
wg.Wait()

won't continue until both workers have called Done().

Also, WaitGroup is usually for:

"Wait until these goroutines finish."

not

"Pause until some condition changes."

For a pause/unpause keybind:

Go
P -> pause
P -> resume

a WaitGroup is the wrong tool because goroutines only finish once. A WaitGroup counter can't be repeatedly decremented and incremented as a pause mechanism. Channels or sync.Cond are designed for that use case.

Go

Go

Go

type Window struct {
    Width, Height int32
    window        *sdl.Window
    renderer      *sdl.Renderer
    texture       *sdl.Texture
    pixels        []byte
}



func filterEvent(e sdl.Event, userdata interface{}) bool {
    return e.GetType() == sdl.KEYDOWN || e.GetType() == sdl.QUIT
}



func NewWindow(width, height int32) *Window {
    err := sdl.Init(sdl.INIT_EVERYTHING)
    util.Check(err)
    window, err := sdl.CreateWindow(
        "GOL GUI",
        sdl.WINDOWPOS_CENTERED,
        sdl.WINDOWPOS_CENTERED,
        width,
        height,
        sdl.WINDOW_SHOWN,
    )
    util.Check(err)
    renderer, err := sdl.CreateRenderer(window, -1, sdl.WINDOW_SHOWN)
    util.Check(err)
    sdl.SetHint(sdl.HINT_RENDER_SCALE_QUALITY, "linear")
    err = renderer.SetLogicalSize(width, height)
    util.Check(err)
    texture, err := renderer.CreateTexture(
        sdl.PIXELFORMAT_ARGB8888,
        sdl.TEXTUREACCESS_STATIC,
        width,
        height,
    )
    util.Check(err)



    sdl.SetEventFilterFunc(filterEvent, nil)
    return &Window{
        width,
        height,
        window,
        renderer,
        texture,
        make([]byte, width*height*4),
    }
}



func (w *Window) Destroy() {
    err := w.texture.Destroy()
    util.Check(err)
    err = w.renderer.Destroy()
    util.Check(err)
    err = w.window.Destroy()
    util.Check(err)
    sdl.Quit()
}



func (w *Window) RenderFrame() {
    err := w.texture.Update(nil, unsafe.Pointer(&w.pixels[0]), int(w.Width*4))
    util.Check(err)
    err = w.renderer.Clear()
    util.Check(err)
    err = w.renderer.Copy(w.texture, nil, nil)
    util.Check(err)
    w.renderer.Present()
}



func (w *Window) PollEvent() sdl.Event {
    return sdl.PollEvent()
}



func (w *Window) SetPixel(x, y int) {
    width := int(w.Width)
    w.pixels[4*(y*width+x)+0] = 0xFF
    w.pixels[4*(y*width+x)+1] = 0xFF
    w.pixels[4*(y*width+x)+2] = 0xFF
    w.pixels[4*(y*width+x)+3] = 0xFF
}



func (w *Window) FlipPixel(x, y int) {
    if x < 0 || y < 0 || x >= int(w.Width) || y >= int(w.Height) {
        panic(fmt.Sprintf(
            "CellFlipped event at (%d, %d) is outside the bounds of the window.",
            x,
            y,
        ))
    }



    width := int(w.Width)
    w.pixels[4*(y*width+x)+0] = ^w.pixels[4*(y*width+x)+0]
    w.pixels[4*(y*width+x)+1] = ^w.pixels[4*(y*width+x)+1]
    w.pixels[4*(y*width+x)+2] = ^w.pixels[4*(y*width+x)+2]
    w.pixels[4*(y*width+x)+3] = ^w.pixels[4*(y*width+x)+3]
}



func (w *Window) CountPixels() int {
    count := 0
    for i := 0; i < int(w.Width)*int(w.Height)*4; i += 4 {
        if w.pixels[i] == 0xFF {
            count++
        }
    }
    return count
}



func (w *Window) ClearPixels() {
    for i := range w.pixels {
        w.pixels[i] = 0
    }
}

go calculateNextState(...)

and inside that goroutine there's a large calculation.

You're asking why not do:

Go
func calculateNextState(...) {
    // calculate rows/cells
 
    pauseMu.Lock()
    for paused {
        pauseCond.Wait()
    }
    pauseMu.Unlock()
}

at the end of the goroutine.

The answer is: you can, if that's where the goroutine's work naturally finishes.

For example, if each worker goroutine calculates one chunk:

Go
func worker(...) {
    processRows(...)
 
    waitIfPaused()
}

then pressing p during processRows() won't stop the current chunk. The worker finishes its chunk and then pauses before starting more work.

That's often exactly what you want because the simulation only pauses at a consistent point.

The real question is:

After calculateNextState() returns, what happens next?

If the goroutine exits:

Go
func calculateNextState(...) {
    processRows(...)
    waitIfPaused()
}

then the pause is pointless because the goroutine is about to die anyway.

But if it loops:

Go
func worker(...) {
    for job := range jobs {
        processRows(job)
 
        waitIfPaused()
    }
}

then it's a good place for the pause check.

So the rule is:

One-shot goroutine → pause at the end usually doesn't help.
Long-lived worker goroutine → pause at the end of each job/chunk is a perfectly reasonable design.
Pause between generations → put the pause after finishing a generation and before starting the next one.

For Game of Life, I would normally pause between turns/generations, because that's the cleanest synchronization point.

        mu.Unlock()

mu.Unlock()

Because sync.Cond doesn't store any state itself. It needs a mutex to coordinate access to whatever condition you're waiting on.

When you do:

Go

What Wait() does

When you call:

Go

Go needs to:

Unlock the mutex.
Put the goroutine to sleep.
Wake up when signalled.
Re-lock the mutex.
Return.

It can only do that if it knows which mutex to unlock and lock.

That's why you pass:

Go
&mu

into:

Go
sync.NewCond(&mu)

    cond.Wait()
}

pause is true.
Before worker calls Wait(), another goroutine does:
Go

cond.Broadcast()
Worker then calls Wait().

Now the wakeup has already happened and the worker sleeps forever.

Go

    cond.Wait()
}
 
mu.Unlock()

and:

Go
mu.Lock()
 
pause = false
cond.Broadcast()
 
mu.Unlock()

The lock ensures checking pause and going to sleep happen as one synchronized operation.

Mutex = protects the variable (pause).
Cond = puts goroutines to sleep and wakes them up.
paused bool = the actual state you're waiting on.
